# Подпись официальных сборок (client attestation)

Официальный сервер ZABOR принимает подключения только от сборок, выпущенных
мейнтейнером. Механизм описан здесь целиком: формат подписи, файлы, переменные
окружения и **порядок безопасного включения на работающем сервере**.

Правовая рамка — [TERMS.md](../TERMS.md) (условия сервиса) и
[TRADEMARK.md](../TRADEMARK.md) (имя и логотип). Код клиента при этом остаётся
открытым по GPL-3.0: форк можно собрать и запустить со своим бэкендом.

## Границы механизма

Секрет подписи попадает в собранное приложение, а приложение распространяется
по GPL-3.0 — значит секрет **извлекаем** из установленного клиента. Это
сознательное свойство, а не недосмотр.

Проверка решает три задачи:

- отделяет официальные сборки от посторонних в обычном, не враждебном случае;
- задаёт норму: подключение чужой сборки требует осознанного обхода;
- делает нарушение условий сервиса доказуемым (обход подписи фиксируется в логе).

Криптографическим барьером против целенаправленного обхода она не является и
не может являться при открытом клиенте.

Исключение — канал `admin`: консоль администратора не публикуется, поэтому её
секрет из общедоступных артефактов не извлекается. Права он всё равно не даёт,
доступ решают логин и пароль администратора.

## Формат токена

```
v1:<channel>:<version>:<unix_ts>:<nonce>:<signature>
```

| Поле        | Значение                                                        |
| ----------- | --------------------------------------------------------------- |
| `v1`        | версия схемы                                                    |
| `channel`   | канал сборки: `official` (релиз), `dev` (разработка), `admin` (админка) |
| `version`   | версия приложения из `app.getVersion()`, например `3.2.2`        |
| `unix_ts`   | момент выдачи, unix-секунды                                     |
| `nonce`     | 16 hex-символов случайности, одноразовый                        |
| `signature` | `base64url(HMAC-SHA256(secret, первые пять полей через ':'))`     |

Каналы подписываются **разными секретами**: релизным, dev и админским. Канал
определяет, каким секретом сервер проверяет подпись, поэтому любой из них можно
сменить или отключить, не затрагивая остальные.

Токен передаётся штатным механизмом SignalR `accessTokenFactory`: заголовком
`Authorization: Bearer` для negotiate и long polling, query-параметром
`access_token` для WebSocket (свои заголовки WebSocket в renderer недоступны).
Фабрика вызывается заново на каждое подключение и каждое переподключение,
поэтому подпись не успевает просрочиться в долгих циклах реконнекта.

## Файлы

| Файл                                                     | Роль                                                       |
| -------------------------------------------------------- | ---------------------------------------------------------- |
| `electron.vite.config.ts`                                | внедряет секрет и канал в **main**-бандл (не в renderer)   |
| `src/main/index.ts`                                      | считает HMAC, отдаёт токен по IPC `get-client-attestation` |
| `src/preload/index.ts`                                   | мост `windowControls.getClientAttestation()`               |
| `src/renderer/src/services/signalr.ts`                    | `accessTokenFactory`, разбор отказа, остановка реконнекта   |
| `src/renderer/src/locales/{ru,en}.json`                  | тексты отказов, ключи `main.connection.clientRejected.*`   |
| `.github/workflows/build.yml`                            | секрет из GitHub Actions в сборку CI                       |
| `src/Zabor.Server/Hubs/ClientAttestationFilter.cs` (бэкенд) | проверка подписи в `IHubFilter.OnConnectedAsync`         |
| `src/Zabor.Server/Program.cs` (бэкенд)                   | регистрация фильтра одной строкой в `AddSignalR`           |
| `src/Zabor.AdminConsole/Program.cs` (бэкенд)              | токен канала `admin` со своим секретом, вшитым в сборку     |

Консоль администратора подписывается **собственным** секретом канала `admin`, а не
релизным: релизный извлекаем из любой опубликованной по GPL сборки десктопа, а админка
никуда не публикуется. Секрет вшит в её исполняемый файл (константа
`EmbeddedAdminSecret`), поэтому при запуске админка спрашивает **только логин и пароль
администратора** — вводить секрет не нужно ни на одном устройстве. Переопределяется
переменной `ZABOR_CLIENT_ADMIN_SECRET`, то есть ротация возможна без пересборки. Порог
`ZABOR_CLIENT_MIN_VERSION` к каналу `admin` не применяется: он задан для десктопных
релизов.

Секрет не хранится в репозитории ни в каком виде. `.env` и `.env.*` перечислены
в `.gitignore`.

## Переменные окружения сервера

| Переменная                 | По умолчанию | Значение                                                  |
| -------------------------- | ------------ | --------------------------------------------------------- |
| `ZABOR_CLIENT_SECRET`      | не задана    | секрет канала `official` (релизы)                         |
| `ZABOR_CLIENT_DEV_SECRET`  | не задана    | секрет канала `dev` (сборки разработки и CI)              |
| `ZABOR_CLIENT_ADMIN_SECRET`| не задана    | секрет канала `admin` (консоль администратора)            |
| `ZABOR_CLIENT_ENFORCE`     | `false`      | `true` ⇒ отклонять подключения; иначе только запись в лог |
| `ZABOR_CLIENT_MIN_VERSION` | не задана    | минимальная версия клиента, например `3.2.3`              |

Канал принимается тогда и только тогда, когда для него задан секрет. Не задан ни
один секрет ⇒ **проверка полностью выключена**. Не задан `ZABOR_CLIENT_DEV_SECRET`
⇒ dev-сборки отклоняются с кодом `unknown_channel`, релизы работают. Не задан
`ZABOR_CLIENT_ADMIN_SECRET` ⇒ то же самое получает админка: в режиме log-only это
безвредно, а при `ZABOR_CLIENT_ENFORCE=true` она потеряет доступ.

Фильтр устроен так, что любая нештатная ситуация — нет секретов, нет
`HttpContext`, неожидаемое исключение — **пропускает** подключение и пишет
строку в лог. Худший исход неверной настройки: проверка не работает. Сервер при
этом продолжает обслуживать пользователей.

## Порядок включения на работающем сервере

Все уже установленные у пользователей сборки (3.2.2 и раньше) подписи не
передают. Если включить отклонение сразу, отключатся все. Поэтому включение
идёт в три шага.

**Шаг 1. Проверка вслепую.** На сервере задать секреты (`ZABOR_CLIENT_SECRET`,
`ZABOR_CLIENT_ADMIN_SECRET`, при необходимости `ZABOR_CLIENT_DEV_SECRET`),
`ZABOR_CLIENT_ENFORCE` не выставлять. При старте в логе появится:

```
[Attestation] log-only; channels=official,admin; minVersion=any
```

Дальше на каждое подключение без валидной подписи пишется строка
`[Attestation] would reject <connectionId>: missing (log-only mode)`.
Никто не отключается. Здесь видно реальную картину: сколько подключений
подписаны, а сколько нет.

**Шаг 2. Выпуск подписанного клиента.** Собрать релиз с тем же секретом (см.
ниже) и выложить на страницу релизов. По логам подождать, пока строки
`would reject` не сойдут почти к нулю — это значит, что пользователи обновились.

**Шаг 3. Включение отклонения.** Сначала убедиться, что задан
`ZABOR_CLIENT_ADMIN_SECRET` и консоль администратора собрана с тем же значением —
иначе вместе с посторонними сборками отключится и доступ к администрированию. Затем
выставить `ZABOR_CLIENT_ENFORCE=true` и перезапустить сервер. В логе:

```
[Attestation] enforcing; channels=official,admin; minVersion=any
```

Откат в любой момент: убрать `ZABOR_CLIENT_ENFORCE` (или задать `false`) и
перезапустить. Полностью отключить проверку — убрать оба секрета.

## Сборка на машине разработчика

### Базовая схема: один секрет, настроенный один раз

Один раз создать в корне репозитория файл `.env` (он и `.env.*` уже в
`.gitignore`, в репозиторий не попадёт) с единственной строкой:

```
ZABOR_CLIENT_SECRET=<секрет>
```

Всё. Дальше `npm run dev`, `npm run build` и сборка релиза выполняются **той же
командой, что и раньше** — никаких дополнительных переменных указывать не нужно.
Канал при заданном секрете автоматически становится `official`
(см. `electron.vite.config.ts`), а на сервере тот же секрет прописывается один
раз в `ZABOR_CLIENT_SECRET`. Сверять ключи на каждый релиз не требуется: секрет
меняется только при ротации (см. ниже).

Итоговое поведение:

| Что собираем                         | `ZABOR_CLIENT_SECRET` | Канал        |
| ------------------------------------ | --------------------- | ------------ |
| всё на машине владельца (с `.env`)   | задан                 | `official`   |
| форк, чужая сборка, PR из форка      | не задан              | подпись не шлётся |

### Необязательно: отдельный канал `dev`

Нужно, только если хочется различать в логах сервера свои отладочные
подключения и релизные, либо отзывать отладочный секрет независимо от
релизного. Для этого при сборке задаётся второй канал:

```
ZABOR_CLIENT_SECRET=<dev-секрет>
ZABOR_CLIENT_CHANNEL=dev
```

Переменные окружения имеют приоритет над `.env`, поэтому релиз можно собрать
поверх dev-настроек, не правя файл:

```bash
ZABOR_CLIENT_SECRET=<релизный-секрет> ZABOR_CLIENT_CHANNEL=official npm run dist:win
```

В `release.bat` (он в `.gitignore`) это те же две строки `set`. На сервере при
этом должен быть задан и `ZABOR_CLIENT_DEV_SECRET`, иначе dev-сборки получат
отказ `unknown_channel`. Если такое разделение не нужно — эту секцию можно
игнорировать целиком.

### Проверка, что секрет попал в сборку

```bash
grep -c "<фрагмент секрета>" out/main/index.js   # должно быть 1
grep -rl "<фрагмент секрета>" out/renderer out/preload   # должно быть пусто
```

Секрет обязан присутствовать **только** в `out/main/index.js`. Если секрета нет
вовсе, сборка соберётся без ошибок, но подпись отправляться не будет: тело
`buildClientAttestation` вырезается как мёртвый код, а IPC-обработчик вернёт
`null`.

CI (`.github/workflows/build.yml`) собирает канал `dev` и подписывает его
отдельным секретом `ZABOR_CLIENT_DEV_SECRET` из GitHub Actions secrets —
релизный секрет в CI не попадает вовсе. Если dev-секрет в Actions не задан, CI
просто собирает неподписанную сборку, и это нормально: артефакты CI никому не
раздаются. Для pull request из форка GitHub секреты не выдаёт, поэтому такая
сборка честно остаётся неофициальной.

Генерация нового секрета:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"
```

## Ротация секрета

Ротация **не является частью выпуска релиза**: один и тот же секрет живёт
сколько угодно релизов. Менять его нужно, только если он утёк или если этого
хочется по иным причинам.

Dev-секрет (если он вообще настроен) меняется свободно: заменить его в `.env`, в
GitHub Actions secrets и в `ZABOR_CLIENT_DEV_SECRET` на сервере. Релизы это не
затрагивает.

Админский секрет тоже меняется свободно, но ровно в двух местах: константа
`EmbeddedAdminSecret` в `src/Zabor.AdminConsole/Program.cs` и
`ZABOR_CLIENT_ADMIN_SECRET` в `/etc/zabor/client.env` на сервере. Порядок: заменить в
обоих, пересобрать админку (`publish_all.bat`), перезапустить сервер. Пользователей
это не касается вообще.

Релизный секрет проверяется и клиентом, и сервером, поэтому смена требует
последовательности, иначе установленные у пользователей клиенты отключатся:

1. Сгенерировать новый секрет.
2. Выпустить релиз, подписанный новым секретом.
3. На сервере временно снять `ZABOR_CLIENT_ENFORCE`, заменить
   `ZABOR_CLIENT_SECRET` на новый, перезапустить.
4. Дождаться по логам обновления пользователей, вернуть `ZABOR_CLIENT_ENFORCE=true`.

Если нужна ротация релизного секрета без окна log-only, поддержку двух релизных
секретов одновременно придётся добавлять в `ClientAttestationFilter` отдельно —
сейчас её нет.

## Коды отказа

Сервер отвечает `HubException` с текстом `ZABOR_CLIENT_REJECTED:<код>`. Клиент
разбирает код и показывает локализованный текст из
`main.connection.clientRejected.<код>`; заголовок экрана меняется на
`main.connection.clientRejectedTitle`. Такой отказ повтором не лечится, поэтому
автопереподключение останавливается до перезапуска приложения.

| Код                | Причина                                              | Что делать пользователю                       |
| ------------------ | ---------------------------------------------------- | --------------------------------------------- |
| `missing`          | подписи нет: старая или посторонняя сборка           | установить сборку со страницы релизов         |
| `malformed`        | токен не разбирается                                 | переустановить приложение                     |
| `invalid_signature`| подпись не совпала: другой секрет                    | установить сборку со страницы релизов         |
| `unknown_channel`  | канал сборки не имеет секрета на сервере             | установить сборку со страницы релизов         |
| `expired`          | расхождение часов больше 5 минут                     | **проверить дату и время**, перезапустить      |
| `replay`           | этот `nonce` уже использован                         | перезапустить приложение                      |
| `outdated_version` | версия ниже `ZABOR_CLIENT_MIN_VERSION`               | обновиться                                    |

Код `expired` — единственный, который регулярно встречается у добросовестных
пользователей: он означает сбитые системные часы, и текст ошибки прямо просит
их проверить.
